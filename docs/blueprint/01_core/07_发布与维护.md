# 发布与维护

本文件是内容更新、合并门、阶段发布、正式收录、上线后排序和故障回退的唯一流程蓝图。它使用 [实现结构](03_实现结构.md#前端技术基线) 中已固定的前端和校验基线，规定跨 M0～M3 的稳定发布边界；不重复工具配置，也不提前创建尚无前端工程支撑的工作流或平台配置。

## 发布输入分类

是否进入网站发布链路由变更语义决定，不能把所有 `docs` 修改一概视为公开内容更新。

| 变更 | 自动处理 | 发布边界 |
| --- | --- | --- |
| `docs/background/`、`docs/blueprint/`、`docs/planning/` 的资料或规范 | 运行仓库文档、结构、引用和契约校验 | 不作为网站内容输入，不因单独修改而发布网站 |
| `docs/content/90_examples/` 中经初审的示例集 | 可以生成显式选择示例集的 demo 构建 | 正式构建必须拒绝引用，不得原地转正 |
| 构建入口选定的正式内容集 | 运行内容契约、网站构建、受影响旅程和人工预览 | 通过确认后才随网站发布 |
| 网站实现、内容适配器或运行时配置 | 运行与影响范围对应的类型、测试和构建检查 | 有用户可见变化时必须进入精确提交预览 |

路径过滤只能在正式内容集和前端目录确定后实现，不能仅因文件位于 `docs/content/` 就假定它会进入公开网站。内容集选择、示例隔离和 background 禁止构建规则继续以 [架构](05_架构.md) 为准。

## 合并请求分类与证据

工作流根据受影响路径与变更语义自动给每个合并请求选择一种门；标签只显示分类结果，不能作为跳过检查的输入。

| 分类 | 适用变化 | 必需证据 |
| --- | --- | --- |
| `preview-required` | 网站实现、前端配置、正式网站内容、示例 demo 内容、地域资源等会产生独立用户可见变化的输入 | 全部适用检查、静态优化构建、精确提交预览和人工验收 |
| `checks-only` | background、blueprint、planning、不会进入网站的研究资料，以及没有独立可见变化的纯维护 | 仓库校验及其影响范围内适用的构建和测试；不生成网站预览 |

混合改动使用 `preview-required`。依赖更新必须运行适用的构建和测试，但 Dependabot 不发布公开预览。未来的 `frontend-gate` 应始终向合并请求报告一个明确状态，再在内部按分类执行适用步骤；不得把整个必需工作流设为路径跳过，导致 Ruleset 长期等待不存在的检查结果。

`preview-required` 使用与精确提交 SHA 对应的不可变 Cloudflare Pages 部署地址。会随新提交移动的分支别名只供日常浏览，不能作为验收证据。仓库公开期间，预览可以公开访问，但必须禁止搜索引擎收录；当前不为预览额外引入 Cloudflare Access。

## 分支、稳定演示与人工验收

开发变更按“任务或 `dev_*` 分支 → `dev` → `main`”流动。任务分支合并到 `dev` 时优先使用 squash，并以符合 Conventional Commits 的合并请求标题形成提交；`dev` 合并到 `main` 时使用标准合并提交，并保持合并请求标题符合相同规范。

`demo_stable` 是 `dev` 中已经完成全部必需检查、精确提交预览和人工验收的当前稳定集成提交，不是额外分支、开发阶段或容许破坏构建的例外。`main` 保留为未来生产来源；Cloudflare 生产分支也保留给 `main`，在 I07 的正式条件通过前不启用自动生产部署。

同一账号主导开发时，不强制要求 GitHub 的 approving review。`preview-required` 合并请求改由产品负责人留下包含以下三项的验收评论：

- 已验收的精确提交 SHA；
- 对应的不可变预览地址；
- 实际检查的页面、视图与交互范围。

出现新的用户可见提交后，旧评论立即失效；agent 不能代替产品负责人完成该确认，也不能在确认前自行合并。工作流、Cloudflare 项目、合并请求模板和 Ruleset 检查只在前端工程已经存在、相关命令能够本地成功执行且首个检查名称已经实际产生后实施，再把稳定检查加入 Ruleset，避免用尚不存在的检查锁死分支。

## 内容更新与发布流程

1. 在任务分支修改规范维护位置。事实变化先更新 background；公开文案仍须经过内容准备和人工审核进入正式内容集，构建不得直接读取 background。
2. 自动执行仓库文档校验和内容契约。必需字段、主键、路由、必需关系与输出链接失效时阻断构建；待补可选项使用明确占位并进入当次报告，不适用项直接省略。网站实现另执行 TypeScript 严格检查、`astro check`、ESLint、Prettier 格式检查、Stylelint、影响范围测试和 Astro 静态优化构建。
3. 对用户可见变化完成优化构建，并生成与精确提交 SHA 对应的不可变预览地址。会随新提交移动的分支别名不能单独作为人工确认依据；无独立可见增量的变更仍须按 H13 已确认原则完成适用的构建和测试。
4. 预览使用禁止搜索引擎收录的配置。`noindex` 只控制收录，不等于访问受限；确需限制访问时继续使用受限 Ubuntu/ECS 或平台访问控制。
5. 产品负责人按 I01 在合并请求中确认。检查单位是 I03 定义的页面适用内容包，并覆盖受影响的地域配置、网站版本和可达状态。常规内容更新只检查受影响页面与有代表性的窄屏、宽屏，不重复完整阶段矩阵；阶段验收才执行 I04 的四类视图与完整代表性任务。
6. 人工确认后若提交再次产生用户可见变化，原确认不再覆盖新提交，必须重新检查新的 SHA 和预览。
7. 所有必需检查与人工确认通过后，先合并到 `dev`；只有另行获准的稳定版本才由 `dev` 合并到 `main`。生产部署从 `main` 的合并提交重新选择正式内容集并构建，不直接把示例预览、`dev` 或未合并分支当成正式版本。
8. 部署后检查首页、受影响页面、404、当前地域与网站版本隔离，以及本次变更涉及的主要恢复路径。部署记录至少能回溯提交 SHA 和生产部署结果，不另建审批数据库。

首个可部署浏览的稳定演示版本仍按 H12 试用 Cloudflare Pages；该试用不固定长期供应商或正式域名。是否继续使用该平台，由产品负责人在第一次真实的 `preview-required` 合并请求验收后决定。

## 阶段节奏

- M0 验证专业网站骨架、技术架构、视觉基线和插件接入面。
- M1 交付首批地域配置、基础购票与观演凭据，以及既定公开历史内容。
- M2 交付黄牛支线、完整七结局导演，并按既定顺序准备后续地域配置。
- M3 交付旧酒神历史网站及其独立内容、搜索、访问内异常进度和高成本视觉。

每阶段单独验收，但这不阻止阶段之间发布必要修正或经审核的内容更新，也不把功能目录中的候选自动升级为实现承诺。P0 决策已经完成；阶段任务重排、排期和验收表仍须产品负责人另行授权，不因 H13 或 I06 自动生成。

## 正式域名与搜索引擎收录

预览阶段保持禁止收录。正式域名和索引只在人工确认以下条件后启用：

- 名称、标志、非官方说明、正式素材权利和发布说明已经确认；
- 生产构建只读取正式内容集，不包含 `docs/content/90_examples/`；
- 当前启用地域配置和网站版本的标题、描述、canonical、`hreflang`、站点地图与真实 404 已校验；
- 未启用、缺少必要资源或未实现当前网站版本的地域组合不生成公开页面或替代索引；
- M3 正式发布时已经用人工确认的泰拉日期替换 `0000`；
- 正式域名的手机和电脑核心任务通过对应阶段验收。

开放收录是独立人工动作，不从部署成功、域名存在或平台环境名自动推断。后续新增地域配置或网站版本时，只把已经完整通过验收的组合加入站点地图和 `hreflang`。

## 上线后功能排序

下一项功能只按当前阶段目标、人工体验反馈和实现成本共同判断，不按功能数量、视觉冲击或入口点击量自动排序。内容、素材和审核准备度可以作为可执行性说明，但不建立机械评分模型。

尚未批准的创意继续保存在 `../../planning/03_后续功能候选.md`。重新评估必须先证明它服务当前页面任务，并由产品负责人批准后才能建立模块、旅程和开发批次。M0 不接入匿名访问统计；后续只有在存在明确产品问题时，才另行选择足以回答该问题的最小统计方案。

## 统计与错误监控

受限 demo 不记录匿名页面访问或交互事件，也不接入前端错误监控。首次面向不受控访客公开测试前，应增加最小错误监控，只收集错误与堆栈、路由、提交或版本、浏览器与设备类别、出错模块；不得收集搜索词、`localStorage` 内容、凭据、正文或用户输入。

访问统计和错误监控是两个独立决定。错误监控的公开测试门不自动批准访问统计，也不预选供应商；若以后确有需要，必须按当时的具体问题和部署环境选择最小实现。

## 发布回退

Git 提交是代码与内容版本的最终来源。发生由当前发布引入的阻断问题时：

1. 找到最近一个已经成功部署并通过校验的生产提交，而不是任意较早提交或预览部署。
2. 可以先用托管平台回退到该生产部署以快速恢复，但平台操作不能成为唯一记录。
3. 随后在仓库中使用 `git revert` 或正常修复提交恢复可发布状态；不得强制推送、重写历史或人工复制旧构建覆盖。
4. 从修正后的 Git 提交重新构建正式内容集并部署，使生产环境和仓库重新一致。
5. 重复最小线上检查，并记录故障提交、恢复提交和生产结果。

代码与内容随同一个提交回退，避免页面实现和内容集错配。带版本号的浏览器本地状态遇到不支持的较新版本时应安全忽略或退化为会话内存，不能让回退后的页面崩溃；当前不为此预建复杂迁移系统。托管平台整体故障不属于旧提交可修复的发布回归，应单独处理。
